# Прогноз снятия наличных по филиалам

Тестовое задание: спрогнозировать дневную сумму снятий наличных (банкоматы и касса вместе)
по каждому действующему филиалу на 30 дней, с 11 мая по 9 июня 2026 года.

Результат лежит в `submission.csv`: 59 филиалов x 30 дней = 1770 строк.

## Результат

Метрика - WAPE, оценка на трёх исторических окнах по 30 дней:

| Модель | 11.04-10.05.2026 | 12.03-10.04.2026 | 11.05-09.06.2025 | Среднее |
| --- | --- | --- | --- | --- |
| Среднее по дню недели за 8 недель | 17,1% | 24,0% | 23,5% | 21,5% |
| План загрузки банка с поправкой на запас | 17,0% | 31,3% | 22,9% | 23,7% |
| **LightGBM (итоговая модель)** | **9,8%** | **11,2%** | **11,7%** | **10,9%** |
| XGBoost на тех же признаках (для сравнения) | 10,6% | 10,6% | 11,6% | 11,0% |

Модель ошибается примерно вдвое меньше, чем действующий план загрузки банка.

## Как запустить

Нужен Python 3.11 и около 4 ГБ свободной памяти. Проверено на Windows 10, ноутбук с 16 ГБ RAM.

```bash
python -m venv .venv
.venv\Scripts\activate            # Linux / macOS: source .venv/bin/activate
pip install -r requirements.txt
```

Положите четыре файла из архива задания в папку `data/`:
`transactions.csv`, `branches.csv`, `cash_ops.csv`, `submission_template.csv`.

Затем по порядку:

```bash
python src/build_daily.py    # транзакции -> data/daily.parquet, 3-4 минуты
python src/prepare.py        # таблица "филиал x день" -> data/panel.parquet, секунды
python src/validate.py       # бэктест и сравнение с бейзлайнами, около минуты (необязательно)
python src/predict.py        # обучение и submission.csv, секунды
```

`python src/diagnose.py` (необязательно) пересобирает таблицы в `reports/`.

## Подход

**1. Сжатие данных.** Журнал на 42 млн операций читается потоком через Polars и сводится
в дневную таблицу. В оперативную память файл целиком не загружается.

**2. Чистка.** Удалены 125 025 дублей `txn_id` (полные копии строк; 17.02.2025 журнал за день
был загружен дважды) и 12 тестовых операций сегмента `internal_test` по 1 млрд сум.

**3. Восстановление потерянных записей.** В двух периодах наличные из филиалов уходили,
а операций в журнале нет: 01.07-15.08.2024 пропали записи банкоматов по всем филиалам,
10-14.11.2025 - все записи четырёх филиалов Xorazm. Обнаружено через баланс наличных:
`план + довоз - инкассация = снятия` (в обычные дни расхождение 0,7% по медиане).
За эти периоды снятия взяты из баланса.

**4. Признаки.**
- Календарь: день недели, число месяца, праздники, разгон перед большими праздниками,
  зарплатные дни (5-е и 20-е, со сдвигом с выходных на рабочий день раньше), день после выплаты.
- Уровень филиала: медиана обычных будней за 4 недели, и недельный профиль филиала.
- Все признаки, которые зависят от прошлых снятий, используют только данные старше 30 дней.
  Горизонт прогноза - 30 дней, поэтому в признаки не может попасть будущее ни на валидации,
  ни при построении итогового прогноза.

**5. Модель.** LightGBM предсказывает логарифм доли `снятия / уровень филиала`. Доля нужна,
потому что филиалы различаются по масштабу в разы, а снятия растут год от года. Логарифм -
потому что эффекты перемножаются (зарплата в канун праздника), а в логарифмах это сложение.

**6. Валидация.** Три окна по 30 дней, повторяющие условия задачи: самое свежее, окно
с Рамазан хайитом и Наврузом, и те же календарные даты год назад с Курбан хайитом.
Вариант модели выбран по среднему WAPE на трёх окнах.

## Внешние данные

- **Даты Рамазан хайита и Курбан хайита** - Python-пакет [`holidays`](https://pypi.org/project/holidays/)
  (Узбекистан). Дата Курбан хайита 2026 (27 мая) сверена с постановлением Президента:
  <https://president.uz/ru/lists/view/9233>.
- **Длительность праздничного эффекта взята из самих данных, а не из официального календаря.**
  Официальные переносы и дополнительные выходные в данных проявляются не всегда: например,
  30.12.2024 - официально выходной, а в данных пик снятий в 2,1 раза выше нормы. Сверка
  календаря с данными лежит в `reports/calendar_check.csv`.

## Ограничения

- **11 мая 2026 - спорный день.** Официально это выходной (перенос с субботы 9 мая).
  В истории такой перенос был один раз (10.03.2025), и снятия были обычными, но воскресенье
  10.05.2026 уже на 28% ниже нормы. Прогноз на этот день - середина между сценариями
  "обычный понедельник" и "праздник" (константа `UNCERTAIN_HOLIDAYS` в `predict.py`).
- **Мало примеров праздников.** Каждый хайит встречается в истории 3 раза, поэтому эффект
  праздников оценён менее надёжно, чем недельный рисунок. В данных Курбан хайит длится 3 дня;
  если в 2026 году низкими окажутся и выходные 30-31 мая, прогноз на них завышен.
- **Филиал B060 открыт 02.02.2026.** У него 98 дней истории и период разгона в начале,
  прогноз по нему менее надёжен.
- **Признаки используют данные старше 30 дней** даже для первых дней прогноза, где доступны
  более свежие. Это упрощение: одна модель на весь горизонт вместо отдельной на каждый день.
- **План загрузки банка в модели не используется.** На период прогноза он представляет собой
  одинаковый недельный шаблон; на валидации признак с планом качество не улучшил.
- **Прогноз точечный.** Он минимизирует WAPE, но для планирования завоза нужен запас:
  недовоз для банка дороже перевоза. Квантильный прогноз не делался.
- **Гиперпараметры LightGBM не подбирались**, взяты умеренные значения по умолчанию.
- **Восстановленные по балансу дни** известны с точностью 2-3%.
